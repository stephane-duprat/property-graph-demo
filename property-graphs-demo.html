3. Understand what duality adds
Recommended here
A graph and a document API over the same tables
Part C exposes a person and an outgoing-link array as one JSON document. Updating that document changes the normalized rows that the existing relational graph reads.
There is no JSON copy to synchronize. The SQL script changes Diego’s city through JSON, reads it through the table and graph, then rolls back. It also adds an edge through SQL and shows it in both the JSON array and the graph.
Normal transaction visibility applies. The writing session sees its changes; other sessions see committed data according to their isolation and snapshot rules.
Optional · DB RU 23.26.1+
A graph derived from the document shape
Part D queries the duality document with JSON_TABLE. One projection provides person rows; another provides one edge row per outgoing array member.
It uses TRUSTED MODE and explicit scalar keys. This combines documented capabilities; a dedicated Oracle example certifying this exact duality-to-graph composition was not found. Run the supplied compatibility script on your instance.
Use this when the document contract matters. For this model, mapping the original tables is simpler and permits ENFORCED mode. No performance equivalence is assumed.





4. Ask a graph algorithm
Part E · DB RU 23.26.2+


Pattern matching finds relationships with a specified shape. An algorithm computes a value for each vertex: a rank, a distance, or a component. DBMS_OGA adds these values to a temporary graph used by the surrounding GRAPH_TABLE query.














Reference calculation: results here are computed locally from the five-person baseline. They are not captured Oracle output. City edits above do not affect these topology-based scores.


SQL to run in ADB
Queries here use PGD_REL_GRAPH, or PGD_COST_GRAPH for distances. The full script also runs PageRank and WCC on PGD_JSON_GRAPH.




Why the cheapest route to Carla takes three hops
The direct edge Alice → Carla has effort 9. Alice → Bob → Elena → Carla costs 1 + 1 + 1 = 3. Fewest hops and lowest cost answer different questions. Bellman-Ford returns the distance, not the edge sequence.
These fictional costs live in a second graph mapping over the existing tables. No source data is changed or copied.
Run this graph DDL before either distance query


Combine PageRank with Alice's two-hop pattern
The algorithm ranks the whole input graph. Then the pattern selects Alice's two-hop destinations. DISTINCT removes Diego's duplicate route. The ranking is not recomputed on that neighborhood.


Before running Part E: use a fresh demo session or intentionally finish the current transaction. Oracle cannot run a graph algorithm with uncommitted changes affecting its graph. Earlier ROLLBACK TO examples may leave a transaction open. Computed scores are temporary; they are not persisted as graph properties.





5. Run it in your ADB-S instance
Download individual scripts below or extract the accompanying ZIP
  1. Use a dedicated empty demo schema. The README contains the own-schema grants and quota setup.
  2. Connect with your existing ADB credentials. In SQLcl run @run_core.sql, or load demo_core.sql into Database Actions and choose Run Script. Keep autocommit off for the SAVEPOINT examples.
  3. Expect five vertices, seven edges, and the three two-hop routes shown above. The scripts print results and raise errors if core assertions fail.
  4. For the optional composition, check database RU 23.26.1+ support and run @run_optional.sql. Its success validates the view-based graph on that instance.
  5. For algorithms, use a fresh session after core setup, check RU 23.26.2+ and run @run_algorithms.sql. In Database Actions run sql/07_algorithms.sql. If Part D succeeded, also try sql/08_algorithms_duality.sql.
  6. Keep the first error if setup fails. Cleanup is separate: review sql/99_cleanup.sql before resetting the demo.
